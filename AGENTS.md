# AI Insights

AI Insights reads a person's local AI coding-agent history (Claude Code, Codex, Cursor, Pi, OpenCode, Gemini CLI), plus chat history the person imports from a data export (Claude, `ai-insights import claude <path>`; ChatGPT, `ai-insights import openai <path>`), and turns it into insights and actionable tips. It ships as an npm package (`ai-insights`) with a CLI, a stdio MCP server, agent skills, and plugin manifests for each harness. `CLAUDE.md` points here.

## How it works

1. **Sources** (`src/sources/<harness>/`) discover transcripts and parse each into a `Session`: numbers, tool metadata and the person's own prompts. No assistant text, no tool output. Chat exports are the exception to discovery: `ai-insights import` (`src/cli/import.ts`) turns one into sessions under `imports/<harness>/` in the store (`claude-chat`, `chatgpt`), which that harness's source then reads.
2. **Store** (`src/store/`) caches parsed sessions, facets and reports under `~/.ai-insights/` (`AI_INSIGHTS_HOME` overrides; `HINDSIGHT_HOME` is still honoured; a pre-0.2 `~/.hindsight/` with no `~/.ai-insights/` is moved there once by the CLI's own commands, leaving a symlink, and stays in use when that cannot be done safely: `src/store/migrate-home.ts`. `resolveHome` only reads, and the session-start reminder and the MCP server never move it).
3. **Analysis** (`src/analysis/`) turns sessions into a `Report`: activity, token usage and cost, and deterministic `Finding`s with evidence. No model involved.
4. **Model-run pass**: the `analyze-ai-usage` skill has the person's own agent read redacted excerpts through the MCP server, write one `SessionFacet` per session using the fixed taxonomy, then a `Narrative`. AI Insights never calls a model API itself.
5. **Render** (`src/render/`) writes one self-contained HTML report.
6. **MCP + CLI** (`src/mcp/`, `src/cli/`) expose all of it.

`src/schema/types.ts` is the contract every module codes against. Read it first.

## Rules

- **Nothing leaves the machine.** No outbound network calls anywhere in `src/`. No telemetry. The one listening socket is `ai-insights serve` (`src/cli/serve.ts`), for viewing the report from another computer through the person's own SSH tunnel: Node `http` bound to `127.0.0.1` only (never `0.0.0.0`, and no option to change that), serving only the written `reports/report.html` at one random path per start, read fresh on each visit, `GET`/`HEAD` only, no listing and no path or query parameters, only for a `localhost`/`127.0.0.1`/`[::1]` Host header (against DNS rebinding), with `no-store`, `nosniff`, `no-referrer`, `frame-ancestors 'none'` and the report's own CSP; it stops on Ctrl-C or after 30 minutes without a request. It accepts local connections and makes none; widening what it binds or serves is a change to this rule. The report makes no network requests and loads nothing from the network (its CSP is `default-src 'none'`). It may contain links a person can click: the Matrix OS link, http(s) links to documentation or tools on suggestions and retention, share links (X, LinkedIn) that open the person's own post with the card caption only when they click them, and, temporarily, one event link: the Slush AI Breakfast Club registration page on luma.com (`src/render/event-banner.ts`), which expires at the breakfast's start on 19 Nov 2026 and is then removed. The one exception to keeping numbers on the machine is the stats share link (`src/render/client/sharelink.js`, decoded by `site/lib/share.ts`): it exists only when the person creates it, in the report or with `ai-insights share` (`src/cli/share.ts`: it runs the same `sharelink.js` on the data block of the report it just wrote, so the link is byte-identical to the report's, lists every line it carries before printing it, and only prints text; `--copy` hands it to the terminal's own clipboard with OSC 52 and the link is also saved to `share-link.txt` in the store), and it carries only the v3 payload: aggregate numbers (optional display name, period, sessions, tokens, estimated spend, active days, longest streak, per-agent session share over coding agents only: chat-export harnesses are left out because the site estimates each agent's tokens from that share), one fun-fact line built from counts, the earned titles and the five work ratios as `{k, v}` key-and-number pairs (the site rebuilds the title and rule wording from a table pinned to `src/analysis/recap/titles.ts`), and the recap cards as data (a fixed card key, a headline and a caption, each built in `sharelink.js` from counts, dates, agent names, checked public model-family names and fixed wording; `tests/render/share-link.test.ts` holds the per-card allowlist), in the URL fragment of the site's `/share` page. v3 adds what lets one account publish from several computers: the store's random device id (`src/store/device.ts`, 16 random bytes in `device.json`; never derived from a hostname, username, MAC address or any hardware detail) and an optional typed device name, each ratio's base count `n`, and, unless the person unticks it, `days`: a bitmap of which dates had activity (no counts, no times). v1 and v2 links (and v2 from a report whose store could not make a device id) must keep working on the site; they publish as the account's one `legacy` device. The site keeps one row per (account, device) in `leaderboard_devices` and adds them up in `site/lib/devices.ts`; public pages never receive a device id, a private device name or the day bitmap (`publicDeviceStats`). Never add project names, paths, prompts or other history content to it; a new field is a deliberate payload version change. The public leaderboard and profiles (`site/`, not `src/`) store that same validated payload, and only when the person signs in on the website and presses Publish on their `/share` page; the package never publishes. Leaderboard and profile numbers are self-reported: never describe them as verified. The website (only `site/`) has first-party PostHog analytics through its `/relay` rewrite; it must never send a URL fragment or a referrer handle from `?ref=` (`site/lib/analytics-sanitize.ts`), and the tool and report stay analytics-free. Referrals (`site/lib/referral.ts`) live in a first-party HttpOnly cookie and are credited only on a first publish. Clerk's middleware and its CSP hosts are limited to the pages in `mountsClerk` (`site/lib/auth-config.ts`: /share, /leaderboard, /u, /account, and the API). The landing page and the docs stay Clerk-free for anonymous visitors: their HTML and the chunks it loads carry no Clerk host or code (`site/scripts/check-build.mjs`), their CSP names no Clerk host, and Clerk's middleware never runs there. Temporarily, until the Slush AI Breakfast Club starts on 19 Nov 2026 (then removed), the proxy sets one more cookie: `aii_fi=1`, readable by page scripts, for 6 hours, only on a landing-page load whose Vercel country header (`x-vercel-ip-country`) is `FI`. It reads that header alone, never the IP address or the city, and the landing HTML stays the same for everyone; the page shows its breakfast section in the browser when the flag is there (`site/lib/breakfast.ts`). /share, /leaderboard and /u are cached pages, the same HTML for everyone (`cachedClerkPage`; the board's `?sort=&page=` URL is rewritten in `site/proxy.ts` to one cached view per sort and page, and `site/lib/board-cache.ts` expires the board and profiles on every write that changes them). Their server render never reads the session, and they load no Clerk code for anonymous visitors either: the account menu, the "you" strip and the publish panel mount Clerk on demand only in a browser with Clerk's signed-in cookie (`components/site/clerk-island.tsx`), and the signed-in person's own standing comes from the private, no-store `/api/leaderboard/you`. On those pages Clerk's middleware (`clerkRun`) runs the satellite sync on a signed-out browser's first visit, then skips it for a day (the HttpOnly `aii_auth_checked` cookie, value `1`); a browser with the signed-in cookie keeps the check on every page load so its session stays fresh; prefetches, client navigations and crawlers skip it. Their Sign in goes through /account/sign-in, which always syncs, and the /share fragment is kept in the tab (`site/lib/pending-share.ts`), never put in a URL. Only a browser with Clerk's signed-in cookie (`site/lib/session-hint.ts`) loads the account menu there, on demand (`site/components/site/session-account.tsx`). A profile photo is stored only when the person opts in (at publish, or with the owner's "Show my photo" switch, `site/lib/photo-route.ts`), read from Clerk on the server, uploaded photos only, and limited to `https://img.clerk.com/`; off is the default.
- **Installing into agents is the agent's own CLI, after a yes.** `ai-insights install` (`src/cli/install*.ts`) and the offer at the end of a run set up the plugin only by spawning `claude plugin …` / `codex plugin …`, which fetch it from GitHub. That is the person's agent doing what they asked, like typing the command, so it is not a network call by AI Insights; but it must never happen without first saying what it adds and to which agents (`install` prints the exact commands) and an explicit yes (or `--yes`), and the offer never appears in CI or when not at a terminal. AI Insights never edits an agent's config file itself; detection only reads the agents' plugin files. Every child process has a timeout and a failure is reported, never thrown.
- **A schedule is opt-in, like install.** `ai-insights schedule daily|weekly|monthly` (`src/cli/schedule*.ts`) is the only thing AI Insights leaves running after a restart. On macOS it is one LaunchAgent (`~/Library/LaunchAgents/app.ai-insights.schedule.plist`, loaded with `launchctl bootstrap gui/<uid>`). On Linux it is one systemd user service plus timer (`ai-insights-schedule.{service,timer}` in `~/.config/systemd/user`). Where there is no user systemd it prints a crontab line, and on Windows a `schtasks` command; it never edits a crontab or runs `schtasks` itself. Before adding anything it prints every file, the exact command line and when it runs, then waits for a yes (`--yes` skips only the question). It never adds a job in CI or when stdout or stdin is not a terminal. Every child process has a timeout, and a failure is reported and what was written is removed. The job starts this install's absolute Node and CLI paths, never `npx` (an npx, pnpm dlx or bunx cache is refused), and gets only an allowlist of settings (`PASSED_ENV`). It runs `schedule run`, which scans offline, rewrites the report, writes `digest.json` in the store (counts and a finding id only, `src/store/digest.ts`, readable by the reminder) and shows a notification through `osascript` or `notify-send`. The notification holds counts only (sessions and hours; the cost only with `--with-cost`), never project names, prompts or paths, and clicking it opens nothing. `schedule off` and `ai-insights uninstall` remove everything it added; `schedule status` lists it.
- **The session-start reminder stays offline and out of the model's context.** `src/nudge/` uses Node built-ins only (it is compiled into `harness/ai-insights/hooks/` for the plugin hook; no npx, which contacts the registry), never throws, exits 0, prints at most one line, and only as hook JSON `systemMessage`, never plain stdout (which agents add to the model's context).
- **Chat exports are imported, never discovered.** `src/sources/claude-chat/` reads a Claude data export only when the person runs `ai-insights import claude <path>`, and `src/sources/chatgpt/` a ChatGPT one only on `ai-insights import openai <path>`; a downloads folder is never scanned. Both stream the zip or JSON (`claude-chat/zip.ts`, `claude-chat/json-stream.ts`; Node built-ins only) and build only the keys their `CONVERSATION_SPEC` names, so assistant text, thinking and reasoning recaps, tool inputs and results, attachment text and names, injected prompt blocks, custom instructions, memories, system messages and titles never reach a `Session`, the cache, an excerpt, the report or a share link (`tests/sources/claude-chat/` and `tests/sources/chatgpt/` plant markers in each to prove it). Zips holding account details, login history, memories or projects (`light_metadata`, `memories`, `projects`) are never opened, and of a ChatGPT export only the `conversations*.json` files are. MCP, connector, plugin and custom GPT tool names are user-specific: count them under one label, never by name. Chat harnesses (`CHAT_HARNESSES`, `isChatHarness`) record no tokens or cost, and no model except ChatGPT's public model family (`modelFamily`): show usage as "not measured", never 0 or an estimate, and keep them out of coding findings, work ratios, friction causes, parallel counts and the share link's per-agent split.
- **Never store or show secrets.** Run prompt and command text through `redact`/`clean` from `src/sources/shared.ts` before it is stored or returned.
- **Parsers never throw on bad input.** Transcript formats are internal and change between versions. Skip what you do not understand and count it in `issues`. Ignore unknown record types.
- **Bound everything.** Cap files scanned, bytes per file, events, array sizes and string lengths. Stream large files; do not read a 60 MB transcript into one string.
- **Keep changes inside one module where you can.** `src/schema/types.ts` is shared by every module: change it deliberately and say why in the pull request.
- **No new dependencies** beyond `zod` and `@modelcontextprotocol/sdk` without asking. Node built-ins only otherwise. Node 20+ must work; newer APIs (for example `node:zlib` zstd) need a graceful fallback.
- TypeScript strict, ES modules, `.js` import suffixes, Zod 4 (`import { z } from "zod"`).
- **Tests first.** Vitest, in `tests/<module>/`. Name the user outcome each test protects. Fixtures are small, hand-written and synthetic: never copy real transcript content, real paths with usernames, or real prompts into the repo.
- Real history on this machine may be read to learn the format and to sanity-check results. Never commit it, quote it in reports, or paste its content anywhere.
- Comments explain why, not what. No comment narrating the change you made.
- Commit early and often on your branch with Conventional Commits (`feat(sources): parse codex rollouts`). Changes reach `main` through a pull request.

## Commands

```bash
pnpm install
pnpm typecheck
pnpm test                 # all tests
pnpm exec vitest run tests/<module>   # one module
pnpm build
```

## Finishing

A change is done when `pnpm check` passes and it is committed. In the pull request say what you built, what you verified and how, and anything you could not do. A known gap stated plainly is worth more than a claim of completeness.
